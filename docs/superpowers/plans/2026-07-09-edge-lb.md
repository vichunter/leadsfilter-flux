# edge-lb (L4 client-IP-preserving front proxy) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put a single HAProxy L4 edge proxy in front of the two existing ingress-nginx controllers so real client IPs reach the apps, while keeping both public IPs mapped to their own controller — on one node, no cloud LB, no MetalLB.

**Architecture:** One HAProxy pod runs in `hostNetwork`, binds each public IP (`178.156.239.214`, `5.161.26.66`) on ports 80/443, and forwards each IP's traffic in **TCP mode** to the matching controller's ClusterIP Service, prepending a **PROXY protocol v2** header. Both controllers switch from `ClusterIP + externalIPs` to plain `ClusterIP` and enable `use-proxy-protocol: true`, so they read the real client IP from HAProxy. TLS still terminates at the controllers (cert-manager untouched at the TLS layer). Client → HAProxy (sees real src, hostNetwork, no kube-proxy SNAT) → PROXY header → controller → app `X-Forwarded-For`.

**Tech Stack:** HAProxy 3.2 LTS (Docker official `haproxy:3.2`), Kustomize/Flux, ingress-nginx Helm chart (unchanged names), cert-manager (challenge type is the subject of a required decision, Task 0).

## REQUIRED DECISION (Task 0) — read before anything else

**Decision (2026-07-09): D3.** Keep HTTP-01; the user cannot automate DNS-01 renewals (can set a DNS record manually once, not per-renewal). Remediation = CoreDNS hosts-rewrite so the in-cluster self-check egresses through edge-lb and gets a PROXY header. Execute **Task 4c**. Skip Task 4a (DNS-01) and Task 4b (hairpin-proxy).


Turning on `use-proxy-protocol: "true"` makes the controllers **reject any connection that does not carry a PROXY header**. cert-manager's HTTP-01 challenge does a **self-check** by fetching the challenge URL *from inside the cluster*, without a PROXY header → the controller answers "broken header" → the self-check fails → **certificates stop being issued/renewed** (cert-manager issue #466). Current issuer (`infrastructure/cluster/cert-manager-issuer/cluster-issuer.yaml`) uses **HTTP-01 for both domains**. If we ignore this, TLS silently breaks weeks later at renewal.

Pick ONE remediation before cutover:

- **Option D1 — switch cert-manager to DNS-01 (recommended).** No HTTP challenge → no proxy-protocol conflict → no extra in-cluster component. Requires a cert-manager-supported DNS provider for `leadsfilter.com` and `homefinanceclub.com` with an API token. Cleanest long-term.
- **Option D2 — deploy hairpin-proxy (fallback).** Rewrites cluster-internal DNS for the ingress hostnames so internal requests (incl. cert-manager self-check) pass through a small HAProxy that adds the PROXY header. Keeps HTTP-01. Extra moving part; upstream `compumike/hairpin-proxy` is Ruby and low-activity (Go reimplementation "ouroboros" exists). Gotcha (Opus review): it edits the CoreDNS Corefile — confirm no clash with existing CoreDNS customization, and do NOT combine with DNS-01 (its `cluster.local` rewrite can break DNS-01).
- **Option D3 — CoreDNS hosts-rewrite, HTTP-01 kept, no extra component (Opus review).** Add a CoreDNS `hosts`/`rewrite` entry mapping `leadsfilter.com`→`178.156.239.214` and `homefinanceclub.com`→`5.161.26.66`, so the in-cluster self-check egresses to the node's own on-NIC public IP → hits edge-lb → gets a PROXY header → nginx serves the challenge. This is "manual hairpin" without deploying hairpin-proxy; relies on Task 1 having put both IPs on the node interface (so the node can reach its own public IP). Note: cert-manager has **no supported skip-self-check flag**, so some form of hairpin is the only way to keep HTTP-01.

**Chosen: D3** (see Decision above). D1/D2 kept below only for reference.

**Do not start Task 5 (enable proxy-protocol) until Task 4c is implemented and verified.** Execute Task 4c (D3). Task 4a/4b are not used.

**Files:**

**Interfaces:**
- Produces: a ConfigMap named `edge-lb-haproxy` in namespace `lf-prod`, key `haproxy.cfg`, consumed by Task 3's Deployment.

- [ ] **Step 1: Write the ConfigMap**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: edge-lb-haproxy
  namespace: lf-prod
data:
  haproxy.cfg: |
    #---------------------------------------------------------------------
    # edge-lb: L4 (TCP) front proxy.
    # Role: terminate nothing, split by destination public IP, forward to
    #       the matching ingress-nginx controller, and hand the controller
    #       the real client IP via PROXY protocol v2.
    # All HTTP-level timeouts/keepalive/limits are owned by ingress-nginx.
    # This proxy only reaps genuinely dead TCP sessions.
    #---------------------------------------------------------------------

    global
        log stdout format raw local0 info
        # Enough headroom for the whole node's public traffic; one process.
        maxconn 60000

    #---------------------------------------------------------------------
    # DNS: backends are addressed by their Kubernetes Service DNS name, not
    # a hard-coded ClusterIP, so a Service re-creation (new ClusterIP) does
    # not require editing this file. HAProxy re-resolves in the background.
    # kube-dns ClusterIP confirmed via: kubectl -n kube-system get svc kube-dns
    #---------------------------------------------------------------------
    resolvers kube
        nameserver dns1 10.96.0.10:53
        # Trust a good answer this long before we bother re-querying.
        hold valid 10s
        # Cache these failure kinds briefly so a momentary kube-dns hiccup
        # does not instantly drop the backend out of rotation.
        hold nx      5s
        hold timeout 5s
        hold refused 5s
        hold obsolete 5s
        resolve_retries 3
        timeout retry   1s
        timeout resolve 1s

    defaults
        mode tcp
        log global
        option tcplog
        # dontlognull: do not spam the log with health-probe/port-scan
        # connections that open and close without sending a byte.
        option dontlognull

        # timeout connect: how long we wait to OPEN the TCP connection to the
        # controller Service. This is in-cluster (pod to ClusterIP), so it is
        # always fast; if it takes >5s the controller is broken, fail quickly.
        timeout connect 5s

        # timeout client: max IDLE time with NO bytes from the client BEFORE
        # the backend session is established. Kept well above any ingress
        # timeout so the controller always decides first; we only cut a
        # client that connected and then went totally silent.
        timeout client 1h

        # timeout server: max IDLE time with NO bytes from the controller
        # during setup. Larger than the controller's own timeouts so HAProxy
        # never fires first on a healthy-but-quiet backend.
        timeout server 1h

        # timeout tunnel: THE important one in TCP mode. Once the session is
        # fully established (through the TLS the controller terminates), this
        # governs max IDLE of the whole bidirectional tunnel — long-poll, SSE,
        # WebSocket, big uploads. Long on purpose so the controller, not the
        # edge, ends these. Raise to 24h if you run permanent WebSockets.
        timeout tunnel 1h

        # timeout client-fin: after the client half-closes (sent FIN), how
        # long we keep the half-open side before reaping it. Prevents FD
        # buildup from clients that vanish without a clean close.
        timeout client-fin 30s

    #---------------------------------------------------------------------
    # Health endpoint for the k8s readiness probe. Bound to localhost only so
    # the probe never touches the public data path. (A tcpSocket probe on :443
    # would open a real PROXY-headed backend connection every cycle — churn —
    # and would report healthy even if nginx were down.)
    #---------------------------------------------------------------------
    frontend healthz
        bind 127.0.0.1:8404
        monitor-uri /healthz

    #---------------------------------------------------------------------
    # 178.156.239.214  ->  leadsfilter (magazin)
    # backend Service: ingress-nginx-nginx-ingress-controller.ingress-nginx.svc
    #   (name confirmed via: kubectl get svc -n ingress-nginx)
    #---------------------------------------------------------------------
    frontend ft_main_http
        bind 178.156.239.214:80
        default_backend be_main_http

    frontend ft_main_https
        bind 178.156.239.214:443
        default_backend be_main_https

    backend be_main_http
        # send-proxy-v2: prepend PROXY protocol v2 header carrying the real
        # client IP. Controller must have use-proxy-protocol: "true".
        # No `check`: single backend on a single node — there is nothing to
        # fail over to, and a plain TCP check would arrive WITHOUT a PROXY
        # header and make nginx log "broken header" noise.
        server main ingress-nginx-nginx-ingress-controller.ingress-nginx.svc:80 send-proxy-v2 resolvers kube init-addr none

    backend be_main_https
        server main ingress-nginx-nginx-ingress-controller.ingress-nginx.svc:443 send-proxy-v2 resolvers kube init-addr none

    #---------------------------------------------------------------------
    # 5.161.26.66  ->  homefinanceclub (lidosbornik)
    # backend Service: ingress-nginx-nginx-ingress-hfc-controller.ingress-nginx.svc
    #---------------------------------------------------------------------
    frontend ft_hfc_http
        bind 5.161.26.66:80
        default_backend be_hfc_http

    frontend ft_hfc_https
        bind 5.161.26.66:443
        default_backend be_hfc_https

    backend be_hfc_http
        server hfc ingress-nginx-nginx-ingress-hfc-controller.ingress-nginx.svc:80 send-proxy-v2 resolvers kube init-addr none

    backend be_hfc_https
        server hfc ingress-nginx-nginx-ingress-hfc-controller.ingress-nginx.svc:443 send-proxy-v2 resolvers kube init-addr none
```

- [ ] **Step 1: Write the Deployment**

Key points baked in: `hostNetwork: true` (see real src IP, bypass kube-proxy SNAT); `dnsPolicy: ClusterFirstWithHostNet` (so cluster Service DNS resolves from a host-networked pod); pinned LTS image; config mounted read-only; `replicas: 1` (only one pod can own host ports 80/443).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: edge-lb
  namespace: lf-prod
  labels:
    app: edge-lb
    role: l4-loadbalancer
spec:
  replicas: 1
  strategy:
    type: Recreate   # host ports 80/443 can be held by only one pod at a time
  selector:
    matchLabels:
      app: edge-lb
  template:
    metadata:
      labels:
        app: edge-lb
        role: l4-loadbalancer
    spec:
      # Both public IPs live on eth0 of node leadsfilter-n1. Pin edge-lb
      # there so it always lands on the node that owns the IPs (correct
      # whether this cluster is single- or multi-node). On any other node,
      # bind() of 178.156.239.214 / 5.161.26.66 would fail. Confirm the
      # label with `kubectl get node leadsfilter-n1 --show-labels`.
      nodeSelector:
        kubernetes.io/hostname: leadsfilter-n1
      hostNetwork: true
      dnsPolicy: ClusterFirstWithHostNet
      containers:
        - name: haproxy
          image: haproxy:3.2
          args: ["-f", "/usr/local/etc/haproxy/haproxy.cfg"]
          # BLOCKER fix (Opus review): the official haproxy image runs as
          # non-root (UID 99) since 2.4 and CANNOT bind ports <1024. In
          # hostNetwork the usual escape (net.ipv4.ip_unprivileged_port_start
          # sysctl) is forbidden by kubelet, and NET_BIND_SERVICE alone does
          # not survive the non-root UID (no ambient caps in k8s). Run as root.
          securityContext:
            runAsUser: 0
          ports:
            - { name: http-main,  containerPort: 80,  hostPort: 80 }
            - { name: https-main, containerPort: 443, hostPort: 443 }
          volumeMounts:
            - name: cfg
              mountPath: /usr/local/etc/haproxy
              readOnly: true
          # Probe the localhost-only monitor frontend, NOT :443 (see cfg).
          readinessProbe:
            httpGet: { path: /healthz, port: 8404, host: 127.0.0.1 }
            initialDelaySeconds: 3
            periodSeconds: 10
      volumes:
        - name: cfg
          configMap:
            name: edge-lb-haproxy
```

### Task 4c: (Option D3 — CHOSEN) Keep HTTP-01; fix the self-check via CoreDNS hosts-rewrite

**This is the selected cert-manager remediation. Do Task 4a/4b instead only if you change the decision.**

**Why it works:** External ACME validation (Let's Encrypt → public IP) already traverses edge-lb and gets a PROXY header — fine. The only breakage is cert-manager's *in-cluster self-check*, which hits the challenge URL without a PROXY header once `use-proxy-protocol` is on. Fix: make in-cluster DNS for the cert domains resolve to the **public IP that edge-lb owns**, so the self-check egresses to edge-lb (which prepends the PROXY header) instead of hitting the controller ClusterIP directly. The public IPs are on `leadsfilter-n1`'s `eth0`, so this hairpin is a local delivery.

**Files:** CoreDNS config in `kube-system` (the backing for the `kube-dns` Service). Confirm whether it is Flux-managed before editing.

`no_reverse` = don't answer PTR for these IPs. `fallthrough` is **mandatory** — without it the `hosts` plugin becomes authoritative for the whole `.` zone and NXDOMAINs everything else (cluster-wide DNS outage). Expected: all empty. If any AAAA exists, add IPv6 mappings to the block (and have edge-lb bind that v6) or remove the AAAA record.

## Risks / weak spots (attack list for the reviewer)

1. **cert-manager HTTP-01 self-check vs proxy-protocol** (Task 0/4x) — highest risk; silent cert-expiry weeks later if unhandled.
2. **Public IP not on node NIC after externalIPs removal** (Task 1) — packets to `5.161.26.66` get dropped; edge-lb bind fails or receives nothing. Must confirm local delivery + bind.
3. **Non-atomic cutover** (Task 5/6) — a window where proxy-protocol is on but traffic still arrives via kube-proxy without a PROXY header → hard outage. Mitigated by single-commit cutover.
4. **Internal callers of the controller Service on 80/443** — any in-cluster client hitting `ingress-nginx-...-controller` by name will break once proxy-protocol is on. Must inventory before cutover.
5. **Health-check + proxy-protocol interaction** — resolved by using no active `check` (single-node single backend). Confirm no failover expectation is lost.
6. **HAProxy timeouts vs ingress timeouts** — edge values must exceed the largest ingress timeout so the controller always decides; verify against any long-op annotations.
7. **Single edge-lb pod = SPOF on the public path** — acceptable on a single node (the node itself is the SPOF), but note it; a `Recreate` restart briefly drops 80/443.
8. **Config duplicate-timeout bug** — the draft `defaults` block must end with exactly one directive per timeout name (see Task 2 note).
